# PLAN: the Companies Act 2006 (United Kingdom), 2006 c. 46: how the 30 part agents share one vocabulary

Status (2026-11-12, written by keel agent coa-k): the core (`coa-core.l4`) and the keel definitions (`coa-definitions.l4`, tests `coa-definitions-tests.l4`) are written and compile on the stable binary 1.6.110 (main, e51181d, 2026-11-11) and on 1.6.109; `check.sh` output is in `NOTES.md`.
How each list below was made: the seams in section 4 were found by reading headings and the Act's own index of defined expressions and are marked as such; the lists in section 6 were generated by three small scripts that read the text (`coa-tools-owners.py`, `coa-tools-seams.py`, `coa-tools-terms.py`; commands at the end of this file) and were spot-checked, not proved. **A seam seen only from headings, or only from a script, is a candidate: check it against the text of your own range before you rely on it.**
The text is a plain-text rendering of the Act from legislation.gov.uk (Open Government Licence v3.0) made by a converter script; it is not the official text. Line numbers are of `ukpga-2006-46.txt` as it is.

## 1. What a part agent does, in order

1. Read your row in section 6 (your ranges, the core names to expect, your seams).
2. Read `coa-core.l4` (read-only: you may not edit it and you never wait for it). Import `prelude`, `daydate` and the core module `coa-core` (the keel's own modules write the last as an `IMPORT` of the file name in backticks).
3. Encode your ranges as the brief says (coverage table, forks, FALSE and NOTHING, Hohfeld table, tests, `check.sh`).
4. If you need a type or constructor the core lacks, define it in your own module under your own prefix and record it in `NEEDS-CORE.md` in your sandbox (name, fields, the sections that need it); the lead hoists it into the core at the merge.
5. If a provision of yours needs an answer another part gives, take it as an INPUT (section 4), never import the other part.

## 2. Naming rule (verbatim from the brief)

- A name defined in two modules that are imported together cannot be used at all, so no two parts may define the same name. Every top-level name (function, constant, type constructor not in the core) a part defines **begins with the section label it implements, in the form `s 4(2)(a) ...`** (the Act's own numbering: `s 2014(d) a household with an elderly member`, `sch 3 para 2 the amount is reduced`; parentheses inside a backtick name parse fine on the stable binary). Types and constructors shared across parts live only in the core.
- A part may not edit the core and never waits for it. If a part needs a type or constructor the core lacks, it defines it in its own module under its own prefix, records it in `NEEDS-CORE.md` in its sandbox, and the lead hoists it into the core at the merge.
- File names: every module of part `X` begins with `X-` (the part's id), and every module of the keel begins with `coa-`.

Two additions from the keel (the first measured on the stable binary, the second a precaution that was not measured):

- A name that must not be reused includes constructors, fields and fixtures: the keel's own types follow the same rule (`s 1159(1) link`, `s 2 enactment`), and two test fixtures with one name were a "multiple definitions" error.
- Core constructors that are single common words are capitalised (`Days`, `Weeks`, `Company`, `Director`) so that a part's own `GIVEN days` or `GIVEN company` does not collide with them. Do not name a `GIVEN` after a core constructor.

## 4. Seams: how a part takes another part's answer

A seam is a provision in one part whose answer another part's provision needs. Parts are separate sandboxes until the merge, so the asking part takes the answer as an INPUT, named for the section it comes from:

- **Name:** `s <answering section> <the question that section answers, in the Act's own words>`, for example `s 283 the resolution is a special resolution`, `s 1121 the officer is in default`, `sch 6 para 2 ...`.
- **Type:** `MAYBE BOOLEAN` by default (JUST TRUE, JUST FALSE, NOTHING), so that "not covered" in the answering section stays "not covered" in yours; the keel's borrowed-term functions already work this way. A NOTHING input makes your answer NOTHING (`-- NOTHING-kind (points outside the text)`), never FALSE. Use `NUMBER` where the asking section needs an amount or a count, `DATE` where it needs a day, and a core type where the core has one. Use plain `BOOLEAN` only for a fact a witness can state, and for the keel answers in the table below that never answer NOTHING.
- **A seam not listed in 4.1 or 4.2:** name the input `s <answering section> <that section's heading, in the Act's words>` (`inputs/HEADINGS.md` gives each heading) and give it the default type above.
- **One input per seam**, declared once in the function that asks; do not restate the answering section's rule.
- The lead wires the answering part's function to your input at the merge (JUST TRUE, JUST FALSE or NOTHING passes straight through).

## 5. Traps on the stable binary (so that thirty agents do not lose the same hour)

Loud (the binary errors, so you will find them; measured by the keel on 1.6.110 unless marked): a section `GIVEN` read by a second rule (`I could not find a definition for the identifier`); sets (`setSize` is unknown); an opaque `DECLARE` with no body (a parse error at the next declaration); `TYPICALLY` on a record field (a parse error); `WAIT UNTIL` is `WAITUNTIL` and an `#ASSERT` must be on one line (both from the brief, not measured by the keel).
A surprise that no error will warn you about: the two supplied builds (1.6.109 and 1.6.110) CHECK AND RUN `REFUSE`, `#ASSERT REFUSED` and `YMD`, although the brief says the stable line does not have them and forbids them. `check.sh` compares those two builds only, so it goes green on them. Do not use them: write `NOTHING` and `Date day month year` (NOTES.md has the measurement).
Silent (exit 0, wrong answer): `NOT a AND b` reads as `NOT (a AND b)` (measured on both builds: `NOT TRUE AND FALSE` is `TRUE`), so bracket every `NOT`; a `MAY` with a `LEST` is read as `FULFILLED` on main when nothing is done, and an input named in an action (`MUST Pay Borrower creditor 10`) matches ANY payload on main, so name the party in a `PROVIDED` guard instead (both from `dialects.md`, not measured by the keel); `l4 run` exits 0 when an assertion fails on a binary older than legalese/l4-ide#518, so read the counts `check.sh` prints (the `encoding-a-subject` skill, step 7); a quote line that differs from the text only in punctuation passes `srcrefs.py` (`source-locators.md`).
Measured by the keel on 1.6.110: a type and a rule defined under a `§` heading in an imported module are visible to the importer (4 assertions satisfied), so `§` headings in a part are safe for names an importer needs; two test fixtures with one name are a "multiple definitions" error at the use; `elem` works on a `LIST OF DATE`; a `@ref` above a `DECLARE` and above a `GIVEN`-led rule check clean with `srcrefs.py check --refs`; a constructor with two NUMBER fields (`a level on the standard scale` 3 0.1) builds and compares with `EQUALS`.
